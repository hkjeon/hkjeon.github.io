## 개요

| 항목 | 내용 |
|---|---|
| 발주처 | 국내 통신사 |
| 기간 | 2024.04 ~ 2024.10 |
| 역할 | PoC 인프라 설계 및 RHOSP16 구축, 마이그레이션 검증 |
| 대상 | 메시징 시스템 (SMS 계열 VNF) |
| 구성 | Director 1 · Controller 3 · Compute 2 (베어메탈) |
| 기술 | RHOSP 16.2, OVN, virt-v2v, Cinder Multi-attach, SAN 연동, NUMA·HugePages |

## 배경

VMware 기반으로 운영되던 메시징 시스템을 OpenStack으로 옮기는 사업이었습니다. **가능한지부터 확인해야 하는 단계**였기 때문에, 플랫폼을 구축하고 실제 VNF를 옮겨 검증하는 PoC를 두 차례 진행했습니다.

단순한 P2V가 아니었습니다. 대상 VNF는 여러 벤더가 각각 개발한 시스템이었고, 클러스터 구성과 공유 스토리지 사용 방식이 제각각이었습니다.

## 플랫폼 구축

PoC를 수행할 인프라를 설계하고 RHOSP16을 구축하는 것이 맡은 범위였습니다. Director를 올릴 KVM 호스트, 컨트롤러와 컴퓨트 노드의 하드웨어·네트워크 설계부터 오버클라우드 배포까지입니다.

폐쇄망이라 설치 자원을 모두 사전에 준비했습니다.

| 항목 | 내용 |
|---|---|
| OS | RHEL 8.4, TUS 채널 RPM 저장소 오프라인 구성 |
| 컨테이너 | RHOSP 16.2 이미지 오프라인 레지스트리 구성 (마이너 업데이트 시연용 두 버전) |
| Director | KVM 호스트 위 VM으로 구성, Undercloud 설치 |
| Overcloud | Controller 3 + Compute 2 베어메탈 배포 |
| 네트워크 | Provisioning / Internal API / Public API / OAM 분리, bond + VLAN |

통신사 VNF 요구에 맞춰 **컴퓨트 노드는 성능 튜닝을 전제로 설계**했습니다. BIOS 단계에서 C-State 비활성화, Turbo Boost 해제, 전력 프로파일 고정을 적용하고, OS 단계에서 CPU Isolation과 1G HugePages, NUMA 토폴로지 기반 배치를 구성했습니다.

VNF 서비스 네트워크는 물리 NIC을 용도별로 나눠 OVS 브리지에 매핑했습니다. 하나의 VNF가 인터페이스를 9개까지 갖는 구성이라, VLAN과 브리지 설계가 까다로웠습니다.

## 마이그레이션 방식 검증

두 가지 방식을 비교했습니다.

| 방식 | 절차 | 다운타임 |
|---|---|---|
| **virt-v2v 변환** | OVF export → 파일 전송 → qcow2 변환 → Glance 업로드 → 인스턴스 생성 | 길다 |
| **신규 배포 + 데이터 동기화** | OpenStack에 VM 배포 → rsync로 데이터 복사 → IP 전환 | 짧다 |

PoC에서는 **전환 가능성 자체를 입증해야 했으므로 virt-v2v 방식을 시연**했습니다. 다만 300GB 기준 변환에만 약 5시간이 걸렸고, 실제 대상 VM은 1.5TB급이 다수였습니다.

그래서 **상용 전환에는 골든 이미지 + rsync 방식을 권고**했습니다.

1. 골든 OS 이미지로 OpenStack에 기본 환경 구성
2. 서비스 정상 동작 확인
3. rsync로 데이터 동기화
4. IP 전환 직전 기존 VM 서비스 중지 후 최종 동기화
5. 기존 VM 셧다운, IP를 신규 VM에 적용

이 방식이면 **다운타임이 IP 전환 구간으로만 한정**됩니다. PoC의 목적은 "되는지"였지만, 실제 사업의 목적은 "서비스 중단을 얼마나 줄이는지"입니다. 둘을 구분해 제안했습니다.

## 부딪힌 문제

**공유 스토리지 구성이 그대로 넘어오지 않았습니다.**

일부 VNF는 SAN 스토리지를 공유 볼륨으로 마운트해 클러스터를 구성하고 있었습니다. VMware에서 OVF로 내보내면 이 디스크는 **껍데기만 나오고 내용이 빠집니다.** 그대로 변환해 올리면 부팅에 실패했습니다.

원인은 단순합니다. VMware와 OpenStack의 스토리지 구조가 다릅니다. PoC에서는 해당 디스크를 제외하고 진행해 검증을 마쳤고, 상용 전환을 위해 **SAN 스토리지를 Cinder 백엔드로 연동하고 Multi-attach를 검증**하는 항목을 추가했습니다.

**UEFI 지원이 제약이었습니다.**

대상 VM이 대용량이라 대부분 UEFI 모드로 동작하고 있었습니다. 그런데 RHOSP 16.2에서 UEFI 인스턴스는 정식 지원이 아니었습니다. 이미지마다 `hw_firmware_type=uefi` 속성을 지정해 대응했고, 상위 릴리스 적용 여부를 별도 검토 항목으로 올렸습니다.

**디스크 용량 산정이 계속 어긋났습니다.**

1.5TB VM 하나를 옮기는 데 Glance 이미지, 인스턴스 디스크, 스냅샷까지 **원본의 세 배 공간**이 필요했습니다. 처음 산정한 용량으로는 변환 중간에 실패했고, 시험 장비 디스크를 RAID 재구성하고 추가 실장하는 작업을 다시 해야 했습니다.

## 장애 복구 검증

전환 가능성만큼 중요한 것이 **옮긴 뒤에도 안전한가**였습니다. PoC 항목의 절반이 여기에 할애됐습니다.

| 시험 | 내용 |
|---|---|
| 서비스 장애 | Keystone·MariaDB 컨테이너 강제 종료 후 복구 확인 |
| 컨트롤러 장애 | 3대를 순차 Power-off 하며 VNF 영향도 확인 |
| 컴퓨트 장애 | 강제 재기동 후 VNF 정상 기동 확인 |
| 백업·복구 | 인스턴스 스냅샷 생성 및 복원 |
| 마이너 업데이트 | 16.2.5 → 16.2.6 롤링 업데이트 중 서비스 영향 확인 |

**컨트롤러 3대를 모두 내려도 컴퓨트에서 동작 중인 VNF는 영향을 받지 않았습니다.** 컨트롤 플레인과 데이터 플레인이 분리되어 있다는 것을 실증한 결과였고, 통신사 입장에서 가장 확인하고 싶었던 부분이기도 했습니다.

2차 PoC에서는 조건을 더 강하게 걸었습니다. **최대 성능 부하를 주면서** 컨트롤러를 내리고, Cinder를 정지시키고, 주요 컴포넌트를 하나씩 죽여가며 VNF 절체가 정상 동작하는지 확인했습니다.

## 배운 것

**"할 수 있다"와 "이렇게 하는 게 낫다"는 다릅니다.**

PoC는 가능성을 보이는 자리라 virt-v2v로 시연했지만, 그 방식을 상용에 그대로 쓰면 다운타임을 감당할 수 없습니다. 검증 결과를 그대로 이관 계획으로 옮기면 사고가 납니다. **시연용 절차와 상용 절차를 처음부터 구분해 설계해야 합니다.**

**마이그레이션의 난이도는 VM이 아니라 그 주변에 있습니다.**

디스크를 변환하는 일 자체는 도구가 해줍니다. 어려운 것은 공유 스토리지 구성, 클러스터 소프트웨어, IP 전환 절차, 벤더 간 역할 분담입니다. 실제로 이번에도 **환경 파악과 VNF 특성 확인에 대부분의 시간이 들어갔습니다.**

**용량은 넉넉히 잡아야 합니다.**

원본 크기만 보고 계산하면 반드시 모자랍니다. 변환본, 이미지, 인스턴스, 스냅샷이 동시에 존재하는 순간이 있습니다. 대용량 VM을 다룰 때는 이 점을 먼저 계산에 넣어야 합니다.
