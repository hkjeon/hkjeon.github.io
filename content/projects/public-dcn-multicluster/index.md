| 구성 | 베어메탈 5대 (혼합형 3 + 컴퓨트 2), 배포·컨트롤러 VM, AZ 분리 |

## 과제

**1. 운영 중인 클러스터의 재구축**

Kolla-Ansible로 구축돼 운영 중이던 환경을 OpenStack-Ansible 기반으로 다시 세워야 했습니다. 이미 서비스 중인 VM 9대를 그대로 옮기는 것이 전제였습니다.

**2. 한 클러스터 안의 두 업무 구역, 두 스토리지**

성격이 다른 두 업무 구역이 하나의 클러스터를 공유하는데, **구역마다 사용하는 스토리지 벤더가 달랐습니다.** 데이터가 구역을 넘나들면 안 되는 업무라 스토리지 분리가 요구사항이었습니다.

**3. 제한된 노드로 컨트롤 플레인과 워크로드를 함께**

베어메탈 5대로 컨트롤러와 컴퓨트를 모두 수용해야 했습니다.

## 수행 내용

### 혼합형 노드와 AZ 분리

베어메탈 3대를 **컨트롤러와 컴퓨트를 겸하는 혼합형**으로 구성하고, 나머지 2대를 컴퓨트 전용으로 두었습니다. 배포 노드와 별도 컨트롤러는 VM으로 올려 물리 자원 소모를 줄였습니다.

노드 수가 적은 환경에서 컨트롤 플레인 HA를 유지하면서 워크로드 자원을 확보하는 방식입니다.

여기에 **Availability Zone을 나눠 구성**했습니다. 컨트롤러 간 통신이 L3로 라우팅되는 환경이라 노드가 물리적으로 같은 구간에 있지 않고, 인스턴스가 어느 그룹에 배치될지 제어할 필요가 있었습니다. AZ로 나눠두면 워크로드를 구역 성격에 맞게 배치할 수 있습니다.

### 구역별 스토리지 분리 — Cinder Multi-Backend

두 벤더의 FC 스토리지를 하나의 Cinder에 함께 물리고, 볼륨 타입으로 구분했습니다.

| 구역 | 스토리지 | 드라이버 | 연결 |
|---|---|---|---|
| A 구역 | Pure Storage | `PureFCDriver` | FC |
| B 구역 | NetApp ONTAP | `NetAppDriver` | FC |

볼륨 생성 시 타입을 지정하면 해당 구역의 스토리지에만 생성됩니다. 구역 간 데이터 분리를 스토리지 계층에서 보장하는 구조입니다.

한쪽 백엔드에는 이미지 볼륨 캐시를 함께 활성화했습니다. 같은 이미지로 VM을 반복 생성할 때 Glance에서 매번 내려받지 않고 스토리지 내부에서 복제하므로 생성 시간이 크게 줄어듭니다.

### 네트워크 설계

물리 NIC을 역할별로 본딩해 세 갈래로 나눴습니다.

| Bond | 용도 | 브리지 |
|---|---|---|
| bond0 | API · Tenant | — |
| bond1 | Provider (서비스) | `br-provider` |
| bond2 | Provider (NAS) | `br-nas` |

**NAS 접근 경로를 별도 Provider로 분리한 것**이 특징입니다. VM이 NAS 볼륨을 붙일 때 서비스 트래픽과 경로가 섞이지 않습니다.

Provider network는 모두 flat으로 구성했습니다. 구역별로 대역을 나누고 VM은 Provider network에 직접 붙는 구조라, 가상 라우터를 거치지 않아 지연이 줄고 Floating IP 관리 부담도 없습니다.

### FC Multipath 구성

각 노드에 HBA를 이중으로 두고 Multipath를 구성했습니다. 노드별 WWN을 사전에 정리해 스토리지 존닝과 대조하는 절차를 문서화했고, 이 목록이 이후 장애 대응과 증설의 기준이 됐습니다.

### VM 이관

기존 환경의 VM 9대를 신규 클러스터로 옮겼습니다. 두 클러스터가 동시에 존재하지 않는 재구축이라, **디스크 이미지를 클러스터 밖에 보관했다가 다시 넣는 방식**을 썼습니다.

| 순서 | 작업 |
|---|---|
| 1 | 별도 NAS를 기존 호스트에 마운트 |
| 2 | 대상 VM의 디스크를 qcow2로 추출해 NAS에 저장 |
| 3 | 기존 환경 철거 후 OpenStack-Ansible로 재구축 |
| 4 | 신규 클러스터 호스트에 같은 NAS를 마운트 |
| 5 | qcow2를 Glance 이미지로 업로드하고 인스턴스 생성 |

**NAS가 이관 통로이자 백업 역할을 겸했습니다.** 재구축 도중 문제가 생겨도 원본 디스크가 클러스터 밖에 남아 있으니 되돌릴 여지가 있습니다.

각 VM의 네트워크 인터페이스와 IP, 연결된 스토리지를 사전에 표로 정리해, 이관 후 동일하게 재현되도록 준비했습니다. Provider network에 직접 붙는 구조라 IP를 그대로 유지해야 했습니다.

## 배운 것

**Multi-Backend는 DR이 아닙니다.**

초기 검토 단계에서는 재해복구 구성까지 기대가 있었지만, Cinder Multi-Backend는 **볼륨을 어느 스토리지에 생성할지 선택하는 기능**이지 복제나 이중화를 제공하지 않습니다. 이 구분을 명확히 하고 요구사항을 다시 정리하는 과정이 필요했습니다.

기능 이름만 보고 기대를 세우면 검수 단계에서 문제가 됩니다. **무엇을 제공하고 무엇을 제공하지 않는지**를 먼저 확인하는 습관이 중요합니다.

**`default_volume_type`이 실제 동작을 결정합니다.**

백엔드를 여러 개 등록해도, 사용자가 타입을 지정하지 않으면 기본 타입 하나로만 볼륨이 생깁니다. 설정 파일에 두 백엔드가 나란히 있다고 해서 자동으로 나눠 쓰이지 않습니다. 구역별 분리를 의도했다면 **볼륨 타입과 기본값까지 함께 설계해야** 합니다.
